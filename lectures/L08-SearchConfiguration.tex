\begin{frame}{Portfolio solvers}
  \begin{definition}
    A \defined{portfolio solver} refers to a solver that has a \textit{collection} of alternative search strategies, or even entire other solvers, that it chooses from.
  \end{definition}
  \vfill
  
  Example portfolio solvers:
  {\small
  \begin{itemize}
  	\item In the Pseudo-Boolean competition, it has become common to first run an ILP solver for limited time, only then start the PB solver on the hard instances.
  	\item Commercial ILP solvers include a local search solver to find good initial solutions and hence a good initial upper bound (for minimisation).
  	\item Modern SAT solvers divide their time between 'focussed mode' (frequent restarts, good for finding SAT solutions) and 'stable mode' (very few restarts and different heuristics, good for proving UNSAT)
  \end{itemize}
  }
  \vfill
  \pause

  Portfolio solvers can contain \textbf{independent solvers}, meaning that their implementations are independent pieces of code, or \textbf{dependent solvers} that do share data structures or other information during search.
\end{frame}


\begin{frame}{Portfolio solvers}
	
	A portfolio can be used in different ways:
	\begin{itemize}
		\item Choosing one solver from the portfolio to run: \textbf{algorithm selection}
		\item Choosing a sequence of time-limited solver runs: \textbf{portfolio sequencing/scheduling}
		\item Choosing which subset of solvers to run in parallel: \textbf{parallel portfolio selection}
	\end{itemize}
	Furthermore, this can be done statically (decided upfront, e.g. through \textbf{algorithm configuration}), or dynamically (choosing which/how long during search, based on the current state).
	\vfill
	\pause
	
	CPMpy is NOT a portfolio solver, because it does not automatically choose which solver to run for you (it defaults to ortools). But you \textit{could} build a portfolio solver on top of CPMpy that would choose a solver intelligently. 
	
\end{frame}

\begin{frame}{Algorithm Selection}
  \begin{center}
    Given a problem, choose the best algorithm to solve it.
  \end{center}
  

	``algorithm'' used in a very loose sense
	\begin{itemize}
		\item constraint solvers
		\item search strategies
		\item modelling choices
		\item different types of consistency
		\item \ldots
	\end{itemize}

  As long as a finite (typically small) set of "algorithms" is available: the \textit{portfolio}.

  \blfootnote{Rice, John R. ``The Algorithm Selection Problem.'' Advances in Computers 15 (1976): 65–118.}
\end{frame}

\begin{frame}{(Automatic) algorithm selection}

Automatic algorithm selection focusses on 'instance specific' configuration:

\begin{itemize}
	\item For an unseen problem instance: which algorithm should I run on it?
	\item Instance-specific: allowed to analyse the instance and decide based on \textit{features} that you can derive from it
	\begin{itemize}
		\item nr of variables, constraints
		\item types of constraints used
		\item structure of the constraint network
		\item probing (run an algorithm for short time, collect statistics)
	\end{itemize}
	\item Portfolio solver developers often hard-code their experience into if/then rules
	\pause
	
	\item In \textit{automatic} algorithm selection, Machine Learning is typically used to build a \textbf{performance model}, and predict which algorithm to use.
	\begin{itemize}
		\item that means you need a \textit{training set} of instances for the ML model
		\item and a \textit{test set} of instances on which to evaluate
	\end{itemize}
\end{itemize}
\end{frame}

  \begin{itemize}
    \item anything you can change that makes sense to change
    \item typically multiple parameters with many values (possibly continuous): a \textbf{large} (possibly infinite) set

\begin{frame}{\textit{Automatic} algorithm configuration}

  Can we do better than grid/random?
  \vfill

  Target exploration to a limited number of promising configurations, within a time budget.
  \vfill

  Example: \textbf{model-based optimisation} (SMBO)
  \begin{itemize}
    \item evaluate a small number of initial (random) configurations
    \item use (probabilistic) Machine Learning to train a \textit{surrogate model} of parameter-performance surface based on this
    \item use an \textit{acquisition function} to decide most promising configuration to try next
    \item repeat, stop when resources exhausted or desired solution quality achieved
  \end{itemize}
\end{frame}

\begin{frame}{Time Budget}
	How much time/how many function evaluations to give to the configurator?
	\begin{itemize}
		\item too much $\to$ wasted resources
		\item too little $\to$ suboptimal result
		\item use statistical tests?
		\item evaluate on parts of the instance set
		\item for runtime: adaptive capping = solver timeout with current best runtime.
	\end{itemize}
    \vfill
    
    Need to evaluate on an unseen test-set to avoid 'over-tuning'.
    \vfill
    \pause
    
    There exists a number of out-of-the-box libraries you can use for parameter configuration \textit{(hyperopt, smac3, ...)}
\end{frame}

\section{Parallel portfolios}

\begin{frame}{Parallel portfolios}
	Almost all computers nowadays have multiple cores.
	\vfill
	
	Why use only one?
	\vfill
	\pause
	
	Idea: try many varied search strategies in parallel.
	\vfill
	
	Some worker is likely to get lucky and find a good solution!
	\begin{itemize}
		\item \textit{Diversity} in strategies can be more important than individual strength
	\end{itemize}
\end{frame}

\begin{frame}{OrTools CP-SAT parallel portfolio deep-dive}
	\begin{center}
		\includegraphics[width=0.7\textwidth]{images/ort_parallel}
	\end{center}
	\vfill
	
	For $n$ workers:
	\begin{itemize}
		\item Start $n/2$ full problem solvers
		\item Start $n/2$ first solution subsolvers. When one has finished, continue interleaving (heuristic) subsolvers in that thread.
	\end{itemize}

\begin{frame}{OrTools CP-SAT parallel portfolio deep-dive}
	This many independent solvers would be wasteful...
	\vfill
	
	What they share:
	\begin{itemize}
		\item Bounds on the objective function
		\item The best 3 solutions found so far
		\item Root-level variable bounds (=unary constraints)
		\item Binary clauses
		\item Some short learned (conflict analysis) clauses
	\end{itemize}
	\vfill
	\pause
	
	Can not share all learned clauses: more sharing is slower sharing, more clauses can lead to slower memory access.
	
\end{frame}

\section{Other parallel paradigms}

\begin{frame}{Other parallel paradigms}
	A parallel portfolio is one parallel paradigm, very good up to a reasonable number of cores (16-24).
	\vfill
	
	What if you want to speed up across \textit{many many} cores? 64+?\\
	parallel exploration of a shared search tree!
	\vfill
	
	Two generic paradigms:
	\begin{itemize}
		\item Embarrassingly parallel search
		\item Work stealing
	\end{itemize}
\end{frame}

\begin{frame}{Embarrassingly parallel search}
	If you can split a problem into \textit{independent} sub-problems, then it becomes (embarrassingly) easy to solve it in parallel.
	\vfill
	
	For search trees: do a breadth-first enumeration up to depth $n$. \\
	E.g. a binary search tree would create $2^n$ independent subtrees:
	\begin{center}
	\begin{tikzpicture}[auto,scale=0.88]	
		\tikzstyle{bbnode}=[circle,draw=black,fill=blue!20,semithick,inner sep=.5ex]
		\tikzstyle{leaf}=[bbnode,green!60!black,fill=green!60!black!20]
		\tikzstyle{var}=[rectangle,node distance=3ex];
		\tikzstyle{txt} += [font=\tiny]
		
		{ \node (root) at (2.25,4) [bbnode] {}; }

		\draw (3.2,3.6) node[txt]{$x \neq 1$};

	\vfill
	
	Each set of choices up to that depth, when added as a constraint, creates an independent subproblem: the best solution across all is the best for the original problem.
	
\end{frame}

\begin{frame}{Embarrassingly parallel search}
	If you can split a problem into \textit{independent} sub-problems, then it becomes (embarrassingly) easy to solve it in parallel.
	\vfill
	
	Pro:
	\begin{itemize}
		\item Easy and fast to do the splitting
		\item No interaction between subproblems needed
	\end{itemize}
	
	Con:
	\begin{itemize}
		\item Workers have to wait for the subproblem splitting to be ready\\
		 (could do depth-limited DFS and a queue)
		\item Subproblems can be very unbalanced: \\
		  some might be trivial to solve, others take as much time as the original problem
		\item Workers become idle when the queue is empty
	\end{itemize}
\end{frame}

\begin{frame}{Work stealing}
	Give the search tree to one worker.\\
	Until finished: if a worker has no subtree, \textit{steal} part of the search tree of another worker.
	\vfill
	
	\begin{center}
		\begin{tikzpicture}[auto,scale=0.88]

\begin{frame}{Work stealing}
	Give the search tree to one worker.\\
	Until finished: if a worker has no subtree, \textit{steal} part of the search tree of another worker.
	\vfill
	
	Pro:
	\begin{itemize}
		\item Workers are never idle: the search tree can always be split further
	\end{itemize}
	
	Con:
	\begin{itemize}
		\item Splitting and its communication needs modified implementations \\
		(e.g. split where, and make sure the original worker does not backtrack over it)
		\item Splitting takes time and does not involve actually searching
		\item Subproblems can be unbalanced, leading idle workers to keep interrupting the busy workers (e.g. with 40+ workers)
	\end{itemize}
\end{frame}

\begin{frame}{Summary}
  Single-thread portfolio:
  \begin{description}
    \item[Algorithm Selection] choose the best \emph{algorithm} for solving a problem
    \item[Algorithm Configuration] choose the best \emph{parameter configuration}
      for solving a problem with an algorithm
  \end{description}
  \vfill

  Parallelism:
  \begin{itemize}
  	\item OrTools CP-SAT as example of a \textbf{parallel portfolio}: full workers, first solution workers and interleaved heuristic workers.
  	\item Embarrassingly parallel search tree splitting
  	\item Work stealing (ad-hoc search tree splitting)
  \end{itemize}
\end{frame}
